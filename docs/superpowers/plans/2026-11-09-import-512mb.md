# Exports import within 512 MB — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An Apple Health, Epic EHI or C-CDA export uploaded through `upload_link` → `import_file` imports on a 512 MB server, with the same records as today, and resumes after a failure or restart.

**Architecture:** The plan starts with a repeatable measurement: synthetic exports and a memory test. The Apple Health importer then writes in deterministic batches while it reads, instead of building everything first; source files and archives upload as streams. `import_file` runs each import as a child Node process with a heap cap. The child saves a job record and a checkpoint in `.ga/imports/<jobId>/`. The gateway resumes unfinished jobs at startup, and a resumed job re-reads the export and skips batches already committed.

**Tech Stack:** Node 26 (strip-only TypeScript), vitest 5.1.0, `@medplum/core` 5.2.14, `node:child_process`, `node:sqlite` store (GA's own) and Medplum.

**Spec:** `docs/superpowers/specs/2026-11-09-import-512mb-design.md`

## Global Constraints

- **Memory budget:** all GA containers together stay within 512 MB during a 2 GB import. The gateway plus the import child gets **190 MiB** (spec [call]: 512 minus the store's 240 and sync's 80). Task 1 re-checks this split against measured numbers, and changing it needs a ledger ruling with the numbers.
- **Same result:** for the same export, the records written are exactly those today's importer writes: same types, identifiers and values, same skips and report counts. Re-importing the same export is a no-op. A newer export updates only changed records.
- **Integrity:** no duplicates. Every dropped record is counted in the report. A resumed import's final report equals an uninterrupted run's.
- **Both stores:** works on Medplum (offsets capped at 10,000, so page by `_lastUpdated`) and on GA's SQLite store. Tests cover both, the Medplum side through the integration project.
- **Import lock:** `withImportLock` is taken per batch, never for a whole import.
- **Kept as-is:** existing identifiers (`urn:ga-server:id:apple-health`, `urn:ga-server:id:ehi:<org>`, `urn:ga-server:id:ccda`), tags, Provenance, the AGENTS.md data rules and the archive DocumentReferences.
- **No real data:** no PHI in tests, fixtures or logs; synthetic exports only; tests never touch the owner's record (Medplum runs use `ga-test*` projects).
- **Dependencies:** none new unless unavoidable (recorded with the reason).
- **Repo rules:** commits in conventional style with no attribution lines, no push. `src/store` stays separable: this plan needs no `src/store` change; if one becomes necessary, follow AGENTS.md "Editing src/store".

## Review Focus

1. **A resume after a crash mid-batch:** a batch interrupted between two writes must end with every record once and the exact report. Test: Task 5 `resume after a crash inside batch 3 writes each record once and reports like an uninterrupted run`.
2. **Two imports at once, or an import while `ga-sync` runs:** per-batch locking must not corrupt either one. Test: Task 3 `an import interleaved with another writer's lock between batches keeps both results`.
3. **An export with a type's records not in date order** (Apple does not promise order): batching must not split a day's summary or drop a blood-pressure pair. Test: Task 3 `shuffled records give the same resources as sorted ones`.
4. **The child process killed by its heap cap:** the job becomes resumable, not "done", and the gateway keeps serving. Test: Task 5 `a child that exits non-zero leaves the job running for resume and the gateway answers /healthz`.
5. **A corrupt or truncated export** (cut mid-line or mid-zip): the import stops with its error and writes no half record. Test: Task 3 `a truncated export.xml fails with its error and no partial batch`.

### Task 3: Apple Health import in deterministic batches

**Files:**
- Create: `src/apple/batches.ts`, `tests/apple-batches.test.ts`
- Modify: `src/apple/import.ts`, `src/apple/readings.ts`, `src/apple/daily.ts`

**Interfaces:**
- Consumes: Task 2's `storeDocument` (through `archiveFolder`).
- Produces:
  - `type Batch = { index: number; resources: Resource[] }`.
  - `appleBatches(dir: string, opts: { size: number; timeZone: string }): AsyncGenerator<Batch, { exportDate: string; skips: Record<string, unknown> }>`. Batches are deterministic: the same export and size give the same batches in the same order.
  - `importAppleHealth(client, cfg, dir, patientId?, opts?: { batchSize?: number; skipThrough?: number; onBatch?: (index: number, report: ImportReport) => Promise<void> })`. It keeps its result type. `skipThrough` means batches with `index <= skipThrough` are read but not written. `onBatch` is called after each committed batch, which is where Task 5 saves its checkpoint.
  - Default `batchSize`: 500 resources, unless Task 1 recommends otherwise.

Algorithm, which the signatures don't determine:
- Readings are emitted as soon as each is complete. Blood-pressure halves wait in a map until paired. `Readings` keeps only a `Set` of emitted keys for `sameReadingTwoSources`.
- Daily summaries are emitted after the read ends. Daily state is per day and type, so it stays small.
- Clinical records and ECGs are emitted last.
- Batches cut the emitted stream every `size` resources.
- The unchanged check runs per batch: one search by identifier for the batch's identifiers, chunked to fit a URL, replacing `existing()`'s whole-record scan.
- Each batch is written with `withImportLock(() => importResources(...))`, and reports are summed with `addReport`.

### Task 5: Import jobs in a child process, checkpoints and resume

**Files:**
- Create: `src/import-jobs.ts`, `tests/import-jobs.test.ts`
- Modify: `src/tools/imports.ts` (use jobs instead of the in-memory map), `src/gateway/server.ts` (resume at startup), `src/cli.ts` (`import-job <jobId>`, internal, not in help), `src/import.ts` (the EHI and C-CDA paths accept `onBatch` and `skipThrough` where they write, else they run as one batch with index 0)

**Interfaces:**
- Consumes: `importAppleHealth` options from Task 3, `unzipSafe` from `src/gateway/uploads.ts`.
- Produces:
  - `type JobRecord = { id: string; kind: ImportKind; upload: string; root?: string; tz?: string; status: 'running' | 'done' | 'failed'; started: string; lastBatch: number; report?: unknown; message?: string; attempts: number }`, stored as `.ga/imports/<id>/job.json` (0600, atomic write).
  - `startJob(dir: string, upload: string, opts: { tz?: string }): JobRecord`, which writes the record and spawns the child.
  - `runJob(dir: string, id: string): Promise<void>`, the child's body:
    1. unzip into `.ga/imports/<id>/root` if not yet done, then delete the zip;
    2. run the import with `skipThrough: lastBatch` and `onBatch` saving `lastBatch` and the summed report;
    3. on success set `status: 'done'` and the report, then remove `root`.
  - `resumeJobs(dir: string): number`: at gateway start, every `running` record gets a new child. Before each start, `attempts` goes up by one. After **3** failed attempts in a row the job becomes `failed` with the last error, and `root` is kept so the failure can be inspected.
  - `jobStatus(dir: string, id: string): JobRecord | undefined`, read by `import_status`.
- Child command: `node --max-old-space-size=<CHILD_HEAP_MB> src/cli.ts import-job <id>`, with the value from Task 1. The child runs with the gateway's `GA_CONFIG` and `TZ`.
